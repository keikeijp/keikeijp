# Jev 型モデル (選択肢 + 確率だけを返すモデル) を dtm-agent に組み込む検討

TypeSafe AI の Jev のように「文章を生成せず、決められた選択肢から選んで確率を返す」モデルを、
dtm-agent のどこに差し込めるかを整理したメモ。元ネタは海外の利用例 15 件をまとめた記事
(2026-09) で、この文書の「事例」の節の数値はすべて **各開発者または提供元の自己申告** であり、
こちらで再実行して検証したものではない。

## 1. 事例 15 件に共通していた構造

```
情報を集める (センサー / DOM / RAM / 音声認識 / 検索)      ← 普通のコード
        ↓
選択肢を絞る (候補を最大 N 件、許可された操作だけ)          ← 普通のコード
        ↓
Jev に「どれか」「どのくらい確からしいか」を聞く             ← ここだけモデル
        ↓
コードで検証して実行する (閾値、フォールバック、停止条件)    ← 普通のコード
```

「AI がゲームをプレイしている」「AI がブラウザを操作している」と紹介されていた事例も、
実際にモデルがやっているのは真ん中の 1 段だけだった。画面を見ているわけでも、
文章を書いているわけでもない。

| # | 事例 | 集める / 絞る (コード) | Jev が答える選択肢 | 実行 (コード) |
|---|---|---|---|---|
| 1 | Mac ランチャー | Swift が候補を最大 15 件 | 対象はどれか / 操作の種類 / Enter で実行してよいほど明確か | Swift。API 断なら通常の曖昧検索に退避 |
| 2 | 列名で分類する表計算 | 列名 + サンプル 3 行で分類形式を決める | 各行の緊急度など | 12 並列で処理、集計を再計算 |
| 3 | 音声ブラウザ | Web Speech API の途中文字起こし + 画面の要素一覧 | 対象 / 意図 / 指示は完了したか / 危険な操作か | Playwright |
| 4 | フライト検索ブラウザ | DOM から候補を整理 | 操作と対象 | 自由入力だけ別の生成モデルが担当 |
| 5 | X 投稿の採点 | 61 問の採点基準 | 各基準のスコア | 書き直し → 再採点。2 回上がらなければ停止 |
| 6 | Claude Code 履歴の圧縮 | ツール呼び出しと結果を組にする | 残す / 結果だけ短くする / 両方落とす | 要約文は作らず原文のまま残す。閾値 0.5 |
| 7 | 洗濯物の通知 | 消費電力 + ドア状態 | 洗濯が終わって中に残っているか | 確率 0.7 が 10 分続いたら通知。日次トークン予算 |
| 8 | スーパーマリオ | RAM から位置 / 速度 / 敵 / 地形を JSON に | 許可された 7 操作のどれか / 危険度 | エミュレーターへの入力 |
| 9 | ポケモン | HP / タイプ / 技 / 状態 | 使える技と交代先から 1 つ | シミュレーター / エミュレーターの両方に接続 |
| 10 | StarCraft | 構造化したゲーム状態 (推論中は一時停止) | 採集 / 生産 / 攻撃 / 探索 | キーボード / マウス入力 |
| 11 | 潜入ゲームの警備員 | 物音 / 扉 / 服装 / 身分証 | 脅威度 / 疑わしさ / 次の行動 / 注目対象 | 6 人の NPC を動かす。確率と根拠を画面に表示 |
| 12 | ドローン | 画像処理で障害物抽出 | 左右に避ける / 上を越える / 止まる / 探し直す | 飛行制御 500 Hz、危険時 50 Hz、Jev は約 2.5 Hz |
| 13 | ルービックキューブ | 解法の工程 (白十字 / 角 / 中段 / 黄色面) をコードで定義 | 今どのケースか | 既知の手順を実行 |
| 14 | 取引ボット | 価格フィード | buy / sell | 既定の公開設定は Jev ではなく模擬モデル。成績の引用は不可 |
| 15 | Doom (公式) | 構造化したゲーム状態 | 移動 / 攻撃 | 毎秒約 10 回の呼び出し |

### 押さえておく制約

- **型が守られることと、判断が正しいことは別。** 選択肢外は返ってこないが、選択肢内で間違える。確率を高く出しすぎることもある。
- **理由を返さない。** 確率だけ。説明が要る場面には向かない。
- **提供元のベンチマーク数値は条件付き。** 評価者が自社チーム、正解基準が他社大型モデルの平均、比較対象を自社の仕組みで構造化出力に縛って計測、価格に補助が入っていないことは証明不可、と提供元自身が書いている。
- **現在は早期アクセス。** 仕様 / 価格 / 提供状況は変わる前提で設計する。
- **失敗の典型は「渡す情報の設計」。** 事例 12 では障害物の高さを渡し忘れたため「上を越える」を選べなかった。プロンプトを直す前に、渡している情報を見る。

## 2. dtm-agent の設計方針との相性

[ARCHITECTURE.md](ARCHITECTURE.md) の方針 1 は「LLM は判断、ツールは事実と実体化」。
これは上の構造そのものなので、Jev 型モデルは **Claude の代替ではなく、Claude が今やっている
"判断" のうち、答えが選択肢で済む小さなものを切り出して肩代わりさせる部品** として入る。

```
                 ┌── 選択肢で済む判断 (再ランク / 分類 / go-no-go) ──→ Judge (Jev 型、~100-300 ms、確率付き)
Claude (tool_runner) ─┤                                                        │ 確率が低い / 引っかかった
                 └── 説明・企画・ノート生成 (文章が要る判断) ←──────────────────┘ ものだけ Claude に戻す
```

この「二段構え」が実務的な使い方で、[ROADMAP.md](ROADMAP.md) v1.0 の
「ローカル LLM / 安価モデルへの一部委譲 (サンプルの再ランクなど)」の具体化に相当する。

## 3. dtm-agent の中で「答えが選択肢で済む」判断

現状のコードを読んで、条件分岐で書きたいが書けていない (または Claude に文章で聞いている) 判断を挙げる。
それぞれ「集める / 絞る / 判断 / 実行」に分解し、**渡すべき情報** (事例 12 の教訓) を明記する。

### 3.1 サンプルの役割分類 (インデックス時) — 本命

- **現状**: `LocalLibrary.build()` の `tags` はファイルパスのトークンだけ。`kick_01.wav` が
  `drums/loop/` にあってもワンショットかループか、キックかスネアかは名前次第。
- **判断**: 各サンプルを固定の選択肢に分類する。
  - 役割: `kick / snare / hat / perc / bass / pad / lead / pluck / vocal / fx / loop_drums / loop_melodic / other`
  - 形態: `one_shot / loop`
  - 用途に耐えるか (無音 / 壊れ / 極端に長い): `usable / unusable`
- **渡す情報**: `duration_sec`, `bpm`, `percussiveness`, `tonalness`, `brightness`, `energy`,
  オンセット数 (1 発か繰り返しか)、パスのトークン。**特徴ベクトル 20 次元をそのまま渡すのではなく、
  人が見て判断できる形に要約してから渡す** (事例 8 / 9 が RAM を JSON に変換しているのと同じ)。
- **実行**: 結果を `entry["role"]`, `entry["form"]` としてインデックスに保存。`search()` で
  `query="kick"` のとき `role == "kick"` を加点、`instrument_hint` との突き合わせにも使える。
- **なぜ本命か**: オフラインの合成音声でテストできる (`tests/conftest.py` と同じ流儀)。
  インデックス時に 1 回だけ呼ぶので、API 断や早期アクセス終了の影響が閉じている。
  判断が外れてもフォールバックはいまのトークン一致で、悪化しない。
- **ROADMAP との対応**: v0.2「パート別に検索」の前提になる。

### 3.2 検索候補の再ランクと採用可否 (`search_samples` の直後)

- **現状**: cosine 類似 + 0.5 × キーワード一致で上位 8 件を Claude に返し、Claude が文章で選んでいる。
  Freesound の結果はキーワードだけで音響類似が効かない (v0.2 で再ランク予定)。
- **判断**: 候補 (最大 16 件) ごとに
  - この依頼 (例: 「1:05-1:21 の雰囲気に合うパッド」) に対して `採用 / 保留 / 不採用`
  - `ライセンス上そのまま使えるか` (Freesound: CC0 / CC-BY / NC の区別)
- **渡す情報**: 依頼文 (英語キーワードに落としたもの)、参照区間の `describe()`、候補の
  `name / tags / duration_sec / score / license / (3.1 の role, form)`。
- **実行**: 採用の確率が閾値 (仮 0.6) 以上のものだけ Claude に返す。全滅なら閾値を下げず
  「該当なし」として Claude に `search_samples` の条件変更を促す。
  事例 1 と同じく **API 断なら現状のスコア順にそのまま戻す**。
- **効果**: Claude に渡すトークンが減り、tool_runner の 1 周が短くなる。判断の説明が要る場面
  (「なぜこのサンプルにしたか」) は Claude が最終的に文章で書くので、Jev が理由を返さなくても困らない。

### 3.3 スケール外ノートの扱い (`add_midi_clip`)

- **現状**: `validate_notes()` でスケール外なら `ok: false` で差し戻す。Claude が
  `allow_out_of_scale=true` で再送するか、ノートを直す。往復で 1 周分のコストがかかる。
- **判断**: 各スケール外ノートを `経過音として妥当 / 直前直後の音にスナップ / 差し戻し` の 3 択に。
- **渡す情報**: 問題ノートの pitch と、**前後のノート** (跳躍幅、拍位置が強拍か弱拍か、長さ)、キー、
  コードトーンか。ノート 1 個だけ渡すと経過音かどうか判断できない (事例 12 の「高さを渡し忘れ」と同型)。
- **実行**: `スナップ` なら `theory.py` のスナップ関数で決定的に直して `warnings` に残す。
  `差し戻し` だけ従来どおり `ok: false`。
- **注意**: 「意図的な半音進行」は Claude の意図であり、Claude 自身が `allow_out_of_scale` で
  表明できる。この判断を先回りしすぎると Claude の意図を潰すので、既定は `差し戻し` 側に閾値を置く。

### 3.4 依頼の明確さと実行可否 (CLI 入口と `realize_in_daw` の直前)

事例 1 の「Enter で実行してよいほど明確か」、事例 3 の「指示はもう完了しているか / 危険な操作か」と同型。

- **入口**: 依頼文を `サンプル探索のみ / MIDI 生成のみ / フル制作 / 質問 / 不明` に分類し、
  参照音声の有無・ライブラリ設定の有無と突き合わせる。`フル制作` なのに `--library` が無ければ、
  tool_runner を回す前に CLI で聞き返す (Claude を 1 周も呼ばずに済む)。
- **`realize_in_daw` 直前**: `ProjectPlan` を要約 (トラック数、各トラックのクリップ数、
  `notes_for_user` の数、`set_project` 済みか) して `実体化してよい / まだ足りない` を判定。
  `ableton` 指定で AbletonOSC に書き込む操作は取り消しにくいので、ここは閾値を高くする。
- **渡す情報**: 依頼文、セッションの状態 (`reference` の有無、`library` の有無、`daw`)、
  `ProjectPlan` の要約。設計図の JSON 全体を渡す必要はない。

### 3.5 メロディの自動評価と停止条件 (ROADMAP v0.3)

事例 5 (採点 → 書き直し → 再採点 → 2 回上がらなければ停止) と同型。

- **判断**: 生成したクリップと参照区間を比べて `音域 / 跳躍 / リズム密度 / 反復` の各軸で
  `参照より少ない / 同程度 / 多い` の 3 段階。
- **渡す情報**: クリップから決定的に計算した統計 (音域の幅、平均跳躍幅、拍あたりノート数、
  同一フレーズの繰り返し率) と、参照区間の `energy / percussiveness / tonalness`。
  ノート列そのものを渡さない。
- **実行**: 「多い / 少ない」の軸だけを Claude に短く返し、書き直しを促す。
  **2 回続けて改善しなければ止める** 停止条件をコード側に置く。書き続けさせない仕組みが本体。

### 3.6 会話の継続 (ROADMAP v1.0)

「もっと暗く」「ベースを 8 分に」を `キー変更 / 密度変更 / 音色ヒント変更 / トラック追加 / トラック削除 / 不明`
に分類し、対象トラックを `plan.tracks` の名前から選ぶ。差分更新ツール群を作るときの入口になる。

### 3.7 tool_runner 履歴の圧縮 (事例 6)

`analyze_reference_audio` の結果 (chroma 12 次元) や `search_samples` の結果 (最大 16 件 × 各フィールド)
は 1 周ごとに履歴に積まれる。`max_iterations=40` を使い切る長い制作では、ツール結果ごとに
`残す / 結果だけ短くする / 落とす` を判定して履歴を詰められる。要約文は作らず原文を残す。
ただし現状は 1 セッションが短く優先度は低い。

## 4. 実装の入れ方 (案)

`SampleSource` と同じく **プロトコル + 差し替え可能な実装** にする。Jev 型モデルの API は早期アクセスで
仕様が変わりうるので、モデル固有のクライアントは 1 ファイルに閉じ込め、既定は決定的なヒューリスティックにする。

```python
# dtm_agent/judge/base.py (案)
class Judge(Protocol):
    def choose(self, *, question: str, options: list[str], facts: dict) -> Choice: ...
    # Choice = (option: str, probability: float)

# 実装
#   HeuristicJudge  : ルールベース。API キー不要。テストとフォールバック用
#   JevJudge        : Jev API。API 断・予算超過なら HeuristicJudge に退避
#   ClaudeJudge     : 確率が閾値未満のものだけ Claude に文章で聞く (二段構え)
```

- `Session` に `judge: Judge = HeuristicJudge()` を持たせ、`search_samples` / `add_midi_clip` /
  `realize_in_daw` のツール内で使う。Claude に公開するツールの入出力は変えない。
- 閾値と日次予算 (事例 7 のトークン予算) は `Session` の設定にする。
- 各判断の `facts` は **人が読める要約** に限定し、特徴ベクトルや設計図の生 JSON は渡さない。
- テストは `tests/conftest.py` の合成音声で `HeuristicJudge` を通し、`JevJudge` は
  `Judge` を満たすスタブで差し替えて確認する。

## 5. 優先順位

| 順 | 判断 | 理由 |
|---|---|---|
| 1 | 3.1 サンプルの役割分類 | オフラインで検証できる。呼び出しがインデックス時に閉じる。v0.2 の前提 |
| 2 | 3.2 候補の再ランク / 採用可否 | Claude に渡す候補が減り、1 周が短くなる。フォールバックが自明 |
| 3 | 3.4 依頼の明確さ / 実体化の可否 | Claude を呼ばずに聞き返せる。Ableton への書き込み前の安全弁 |
| 4 | 3.5 メロディ評価と停止条件 | v0.3 の項目。統計の計算が先に必要 |
| 5 | 3.3 スケール外ノート | Claude の意図と衝突しうるので、閾値の設計を先に決める |
| 6 | 3.6 / 3.7 | v1.0 の項目。差分更新ツールが先 |

まず 3.1 だけを実装し、`HeuristicJudge` で役割分類が回ることを確認してから、Jev 型モデルの
API に差し替えて精度を比べる。比べる指標は「`query="kick"` の上位 8 件に本当のキックが何件あるか」
のような、こちらで再実行できるものにする。

## 6. やらないこと

- Claude の役割 (依頼の解釈、ノート列の設計、ユーザーへの説明) を Jev 型モデルに置き換えること。
  文章が要る判断は今まで通り Claude。
- 音響解析 (BPM / キー / 類似度) をモデルに任せること。方針 1 のとおり決定的なコードで行う。
- 提供元やデモの数値 (速度・費用・勝率) を根拠に採用を決めること。自分の環境で測った数字だけを使う。
